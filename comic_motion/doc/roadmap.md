# 路线图（roadmap）

> 定位：**方向性规划，非排期承诺**。优先级与排期随嵌入方反馈调整。
> 任何路线落地都不得破坏两条既有红线：核心包纯 Dart 零 Flutter 依赖；
> 同 seed + 同 config 逐字节复现契约。每项标注：价值 / 工作量级 /
> 依赖决策点。
>
> 工作量级口径：**S** ≤ 2 天 ｜ **M** ≤ 1 周 ｜ **L** 2–4 周 ｜ **XL** > 1 月
> （以单人专注开发计，含测试与文档）。
>
> **W8 刷新记录**：以下条目已实施并从本路线图移除——
> ① GPU 变换类 MVP（`comic_motion_shaders` 0.1.0：parallax / breathing /
> lightSweep / vignette 单一 uber-shader 实时化，消费 `exportLayers`
> 分层纹理集）；② 分格感知分层（核心包 `panelAware`：横向白带检测 +
> 逐格分层 + 格内 rank 归一视差）；③ AI 深度接口化（`DepthEstimator`
> 抽象接口 + `MotionPipeline(depthEstimator:)` 注入 + `exportLayers`
> 分层纹理集导出 + `doc/external-depth.md` 外部 ML 指南）。

## R1 shader 粒子类效果 GPU 化（comic_motion_shaders 二期）

**现状**：`comic_motion_shaders` 0.1.0 已实时化四件**参数化变换**效果
（parallax / breathing / lightSweep / vignette）。**粒子类**（`ambient`
氛围粒子、`rain` / `snow` 等天气类）仍只在预渲染管线里可用。

**方案**：粒子状态在 fragment 侧程序化重建——把粒子参数（数量/速率/
风向/种子）编码进少量 uniform，shader 内用确定性哈希从 uv + time 重建
粒子轨迹（免 compute/SSBO，避免 uniform 数组数量受限）。与预渲染管线的
粒子观感对齐需要逐效果调参。

**价值**：实时路径覆盖全部 32 效果中的动态主力；粒子类效果在实时侧
无限时长、无循环接缝（预渲染 GIF 受时长与循环点约束）。

**工作量级**：**L**（每效果粒子模型 fragment 化 + 观感对齐 + 双后端验证）。

**依赖决策点**：
1. **观感对齐口径**：实时粒子与预渲染粒子允许多大观感差异（实时路径无
   seed 契约，逐字节一致不适用）；
2. **Web 兼容**：fragment 粒子在高粒子数下的移动端填充率压力，需性能
   矩阵实测。

## R2 AI 模型深度（仍守接口注入路线）

**现状**：深度接口已就位——`DepthEstimator` 抽象接口（`estimate` 返回
`DepthMap`）、`MotionPipeline(depthEstimator:)` 注入点、内置启发式实现
为缺省（行为逐字节不变）、`exportLayers` 分层纹理集导出、
`doc/external-depth.md` 外部 ML 适配指南（含 tflite 最小示例）。启发式
估深的失准场景不变：复杂分格、跨格气泡、主体与背景对比度低。

**方案**：单目深度 / 显著性主体模型（开源轻量模型 + 量化）产出逐像素
深度图，适配 `DepthEstimator` 接口注入。原生依赖按侵入度排序：
1. **服务端**（首选）：`comic_motion_server` 增加深度图端点 / CLI
   `--depth-map` 输入——原生依赖只落在服务端，客户端包依旧纯 Dart；
2. **可选伴生包**：端侧推理（平台通道 + 各平台推理运行时），opt-in，
   核心不感知；
3. 端侧 FFI 直连：破坏纯度面最大，不推荐。

**价值**：语义级分层质量跃升——人物/主体从背景正确分离，是「观感对齐
鸿蒙」在复杂画面上的最后一块拼图。

**工作量级**：**XL**（模型选型/量化/许可审查 + 推理适配 + 深度图注入
回归评估集）。

**依赖决策点**：
1. **卖点边界**：是否接受「服务端/可选包有原生依赖、核心保持零」的
   分层卖点口径；
2. **模型来源与许可**：开源单目深度/显著性模型的推理许可与再分发条款；
3. **panelAware 协同**：逐格注入外部深度图的数据结构（格 × 深度图）
   需与既有 per-panel 管线对齐。

## R3 animated WebP 备选（opt-in 输出格式）

**现状**：`doc/webp_research.md` 调研结论——`image` 4.10.1 已内置动画
WebP 编码（VP8/VP8L + ANMF 容器），零新增依赖即可实现。V3 决策选
**APNG** 的决定性原因：APNG 走流式容器（内存 O(单帧)，与帧序列管线
同构），WebP 编码器需**整帧序列驻留内存**（1080p × 48 帧量级达数百 MB，
移动端不可行）；APNG 体积与浏览器支持在本场景并不吃亏。

**激活条件**（满足其一再评估）：
1. `image` 包支持流式/逐帧 WebP 编码（关注上游 issue 进展）；
2. 出现体积强敏感场景（真彩色体积 ≈ GIF 的 1/3–1/2），且运行端内存
   宽裕（桌面/服务端批量管线先行）；
3. 真彩色动图在 iOS 端需要非 APNG 容器的兼容性回退。

**工作量级**：**S**（适配输出通路 + opt-in `outputFormat` + 逐字节契约
按「锁定版本内」口径回归）。

**依赖决策点**：
1. `image` 包升级会改变既有编码字节——复现承诺按 README「复现承诺与
   边界」的锁定版本口径执行，升级须走版本对齐流程
   （`doc/release_checklist.md`）；
2. WebP 有损模式的确定性边界（编码器内部无随机，但量化决策与版本绑定）。

## R4 多轴交互帧集进阶（V1 路线）

**现状**：V1 交互帧集已支持 phaseX / phaseY 双轴（`both` 导出，
`ParallaxGyroView` 按展示位取轴）。交互维度止步于平面倾斜。

**方案**：扩展第三个交互轴（候选：缩放呼吸相位 / 光照角度 / 页内旋转），
帧集从「双轴网格」升级为「双轴网格 + 独立第三轴帧层叠加」（避免 M³
组合爆炸：第三轴不进网格，作为独立帧序列在 widget 侧叠加或 uniform
混合）。

**价值**：交互观感再进一档（光照跟手 / 缩放景深）；与 R1 实时路径
互补——帧集路线守住低端设备的交互体验上限。

**工作量级**：**M–L**（核心包第三轴导出通道 + 索引格式 v2 + widget 侧
叠加渲染 + 回归）。

**依赖决策点**：
1. **第三轴选型**：缩放 / 光照 / 旋转按嵌入方反馈排序；
2. **索引格式兼容**：`index.json` v2 需向后兼容 v1 读取路径；
3. **与 shader 路径的分工**：第三轴若实时路径先落地，帧集侧是否跟进
   以实测体验差为准。

## 非目标（明确不做）

- **视频编码输出**（WebM/MP4）：必须原生依赖，与核心纯度冲突；嵌入方
  需要视频可自行转码帧序列。
- **核心包引入 Flutter / 原生依赖**：任何路线都以伴生包形态落地。
- **实时交互渲染进核心包**：GPU 路线由独立 shader 包
  `comic_motion_shaders` 承担（变换类 MVP 已落地），核心包保持纯 Dart
  预渲染路线不变。
